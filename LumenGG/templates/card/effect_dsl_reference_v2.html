실행 계약

  • DSL은 JSON 객체이며 현재 schema_version={{ dsl.schema_version }}만 허용합니다.
  • 명령은 위에서 아래로 결정적으로 실행됩니다. 무작위 선택은 세션 RNG를 사용하고 결과 ID가 이벤트에 기록됩니다.
  • 효과 해결은 명령/이벤트 최대 500단계, 이벤트 깊이 64에서 중단됩니다.
  • 명령 전체는 세션 트랜잭션 안에서 처리됩니다. 자동 실행 오류 시 상태 변경을 롤백하고 세션을 수동 모드로 전환합니다.
  • 플레이어 식은 "p1", "p2", {"controller":true}, {"opponent":true}를 사용합니다.
  • 존: {% for zone in dsl.zones %}{{ zone }}{% if not forloop.last %}, {% endif %}{% endfor %}

등록 Python 핸들러

능력에 handler를 쓰면 effects 대신 등록 함수를 호출합니다. 함수 시그니처는 handler(state, context, ability) -> list[effect command]입니다.

  • @effect_handler(name, deterministic_tests=(...))로 등록하며 이름은 전역에서 유일해야 합니다.
  • 전달받은 state/context와 DB를 직접 수정하지 않고 새 DSL 명령 배열만 반환합니다.
  • 시간, 네트워크, 전역 난수에 의존하지 않아야 합니다. 무작위는 random_select 명령으로 반환합니다.
  • 게시 검증은 등록 여부와 핸들러 소유 결정적 테스트 존재/통과를 검사합니다.
  • 일반 조건·값·선택·예약·대체 조합으로 표현 가능하면 핸들러를 만들지 않습니다.

검증·게시 계약

  1. validate_effect_definition은 타입, 열거형, 필수 필드, 선택 기본값, 핸들러 등록을 검사합니다.
  2. 게시 검증에서는 reviewed=true, 루트/능력 draft=false, 효과 텍스트의 명시적 정의 또는 no_effect 재정이 필요합니다.
  3. 각 게시 능력에는 루트 또는 능력 수준의 룰북/Q&A/카드 원문 출처가 필요합니다.
  4. review_evidence에는 각 능력별 최소 3개의 passed=true, deterministic=true 상황이 있어야 하며 scenario_count가 합계와 같아야 합니다.
  5. 검수 완료 저장 시 현재 원문과 Q&A의 승인 해시가 생성됩니다. 이후 원문/재정이 바뀌면 재검수가 필요합니다.
  6. 릴리스 게시 전 python manage.py validate_automatic_ruleset, 이후 python manage.py publish_automatic_ruleset VERSION 순서로 실행합니다.
